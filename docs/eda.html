Data Prep & Exploratory Analysis

Data Gathering Methodology

To establish a robust analytical framework for this research topic, a multi-tiered data ingestion pipeline was constructed using Python to interface directly with official, publicly available data provided by Major League Baseball (MLB) through their public API. This granular information is crucial for researching behavioral trends, game progression tracking, and performance distributions, as it eliminates manual gathering bias and ensures precise records.

The ingestion workflow leverages an established Python wrapper library, MLB-StatsAPI, which acts as an interface layer to efficiently query the underlying REST endpoints. Once retrieved, the raw JSON payload streams are programmatically mapped into tabular structures, optimized for relational database insertion, and permanently stored within a structured local Microsoft SQL Server environment for downstream modeling tasks.

API Reference and Endpoints

The execution of the data pipeline relies on the official MLB StatsAPI framework. Data gathering targets specific configurations across four distinct core API endpoints to compile lookup tables and comprehensive play-by-play data:

Endpoint Name Parameters Data Grabbed
sports_players "sportId": 1, "season": 2026 Fetches lookup table for every player who played in the MLB in 2026
teams "sportId": 1, "season": 2026 Fetches lookup table for all 30 MLB teams
schedule "sportId": 1, "season": 2026, "gameTypes": "R" Fetches complete schedule for the 2026 MLB regular season. Also contains flag indicating once a game is final and its play-by-play data is ready
game "gamePk": 824513 (unique by game, grabbed from schedule lookup) Fetches the complete play-by-play data for a specific, completed game

Data Cleaning and Database Management Pipeline

Raw information obtained directly through an API rarely conforms to strict database schemas without deliberate refinement. A comprehensive programmatic data normalization routine was implemented to guarantee structural completeness and data integrity across all downstream datasets:

Flattener Mechanics for Hierarchical Objects

API results natively bundle multiple metadata entities into deep JSON object trees. To eliminate nesting complexity, isolated custom mapping functions safely traverse dictionary elements, exposing underlying categorical properties like handedness variables (batSide, pitchHand) for players and target grouping classifications, like leagueId and divisionId for teams, into clean database fields.

Constraint Enforcement and Datatype Alignment

Textual timestamps are parsed and converted explicitly into unified temporal representations (pd.to_datetime), establishing compatibility with target database storage constraints. Additionally, standard floating-point approximations are strictly monitored, and structural tracking values (such as scores, indexes, and rosters) are cast directly into nullable integer forms (Int64) to accommodate standard missing database records without triggering system crashes.

Historical State Reconstruction

Because the live game feeds compile final aggregate summaries, an algorithmically driven state machine tracks events backwards chronologically. By systematically tracing the running delta of play outcomes, the data pipeline calculates and injects pre-event base-running status (runnerOn1st, runnerOn2nd, runnerOn3rd), dynamic evaluation scores (prePlayHomeScore, prePlayAwayScore), and remaining team verification challenge levels before each pitch occurs. The current catcher for each team is also tracked dynamically using the starting lineups and substitution events.

Database Duplication Safeguards

To maintain clean data integrity during parallel operational execution cycles, an automated key purge protocol clears out pre-existing database indices matching specific parameters (DELETE FROM pitch_by_pitch WHERE gamePk = :game_pk) prior to parsing new additions. This prevents duplicate primary key constraints or broken tracking data arrays.

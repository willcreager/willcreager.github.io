Data Prep & Exploratory Analysis

Data Gathering Methodology

To establish a robust analytical framework for this research topic, a multi-tiered data ingestion pipeline was constructed using Python to interface directly with official, publicly available data provided by Major League Baseball (MLB) through their public API. This granular information is crucial for researching behavioral trends, game progression tracking, and performance distributions, as it eliminates manual gathering bias and ensures precise records.

The ingestion workflow leverages an established Python wrapper library, MLB-StatsAPI, which acts as an interface layer to efficiently query the underlying REST endpoints. Once retrieved, the raw JSON payload streams are programmatically mapped into tabular structures, optimized for relational database insertion, and permanently stored within a structured local Microsoft SQL Server environment for downstream modeling tasks.

API Reference and Endpoints

The execution of the data pipeline relies on the official MLB StatsAPI framework. Data gathering targets specific configurations across four distinct core API endpoints to compile lookup tables and comprehensive play-by-play data:

Data Cleaning and Database Management Pipeline

Raw information obtained directly through an API rarely conforms to strict database schemas without deliberate refinement. A comprehensive programmatic data normalization routine was implemented to guarantee structural completeness and data integrity across all downstream datasets:

Flattener Mechanics for Hierarchical Objects

API results natively bundle multiple metadata entities into deep JSON object trees. To eliminate nesting complexity, isolated custom mapping functions safely traverse dictionary elements, exposing underlying categorical properties like handedness variables (batSide, pitchHand) for players and target grouping classifications, like leagueId and divisionId for teams, into clean database fields.

Constraint Enforcement and Datatype Alignment

Textual timestamps are parsed and converted explicitly into unified temporal representations (pd.to_datetime), establishing compatibility with target database storage constraints. Additionally, standard floating-point approximations are strictly monitored, and structural tracking values (such as scores, indexes, and rosters) are cast directly into nullable integer forms (Int64) to accommodate standard missing database records without triggering system crashes.

Historical State Reconstruction

Because the live game feeds compile final aggregate summaries, an algorithmically driven state machine tracks events backwards chronologically. By systematically tracing the running delta of play outcomes, the data pipeline calculates and injects pre-event base-running status (runnerOn1st, runnerOn2nd, runnerOn3rd), dynamic evaluation scores (prePlayHomeScore, prePlayAwayScore), and remaining team verification challenge levels before each pitch occurs. The current catcher for each team is also tracked dynamically using the starting lineups and substitution events.

Database Duplication Safeguards

To maintain clean data integrity during parallel operational execution cycles, an automated key purge protocol clears out pre-existing database indices matching specific parameters (DELETE FROM pitch_by_pitch WHERE gamePk = :game_pk) prior to parsing new additions. This prevents duplicate primary key constraints or broken tracking data arrays.

Relational Database Schema

The ingestion pipeline maps the incoming data streams directly into a structured, relational database. This relational setup ensures strict transactional integrity, minimizes structural redundancies, and establishes normalized relationships across game schedules, team identifiers, rosters, and pitch-by-pitch statistics.

1. Schedule Table (schedule)

The schedule table acts as the chronological anchor for the entire dataset. It logs unique game identifiers, calendar dates, competition levels, and the corresponding home and away team entities. It also marks which games are complete and are ready to have their play-by-play data ingested.

2. Teams Table (teams)

The teams table catalogs individual franchise metadata. It maps unique team identification codes to their official club naming conventions, geographic venues, and organizational codes.

3. Players Table (players)

The players table functions as the master athlete index. It maintains unique player biometric associations, birth dates, and names, serving as a relational lookup for player id columns in the pitch by pitch table.

4. Pitch-by-Pitch Table (pitch_by_pitch)

The continuous pitch_by_pitch transactional table serves as the primary data matrix for analytics. Due to the high dimensionality and extensive feature count tracking spatial coordinate parameters, the schema layout is viewed below across three segmented screenshots.

Entity-Relationship & Key Mapping

The architecture of the database relies on strict relational integrity constraints. The pitch_by_pitch table acts as the central transactional hub, utilizing foreign keys to map specific event metrics to granular entity dimensions across the supporting lookup tables.

  • Athlete Mapping: The primary key identifier id within the players table serves as a relational anchor for multiple tracking parameters in the main transactional table. Specifically, it maps directly to batterId, pitcherId, and catcherId inside the pitch_by_pitch table, allowing downstream classification tasks to isolate performance profiles by specific player roles.
  • Game Mapping: The primary key gamePk in the schedule table creates a strict one-to-many relationship with the corresponding gamePk column in the pitch_by_pitch dataset. This ensures that every tracked pitch event maps to a single verified game, tracking dynamic state metrics across a temporal progression.
  • Team Mapping: The unique entity key id within the teams master index maps outward to multiple operational contexts. It resolves home and away match-up contexts by linking to both the homeTeamId and awayTeamId parameters within the schedule and pitch_by_pitch matrices.

Data Subsets, Temporal Constraints, and Feature Engineering

Because the regular season remained ongoing at the start of the initial EDA process, specific structural boundaries were established to preserve the consistency of the exploratory data analysis pipeline. For reasons of analytical timeliness and processing efficiency, a temporal constraint was applied to isolate a data subset containing records logged exclusively up through the end of August. Furthermore, data cleaning required the exclusion of four specific games from the pitch_by_pitch table. These events were contested at alternative venues lacking the necessary Hawk-Eye optical tracking camera arrays, leaving the ABS challenge system unavailable.

Pipeline Extraction: Baseline Data Subsets (pitch_by_pitch_Subsets.sql)

The query script pitch_by_pitch_Subsets.sql isolates and partitions transactional records into two distinct analytical matrices. By filtering pitch events through tailored conditional parameters, this program segments player tracking fields based on specific positional roles. This approach prevents data leakage and ensures clean dimensions for downstream machine learning tasks. It also eliminates any records where a challenge was not possible, leaving just the relevant data.

  • Defensive & Catcher Subset Matrix: MLBData-ABSChallengeablePitches-Defense.csv

Extracted Subsets Overview

  • Batter Subset: This dataset isolates game situations where the batter could challenge (pitch was called a strike and his team has at least one challenge remaining). Features are grouped to capture strike zone discipline metrics, individual challenge success frequencies, and response vectors relative to umpire call inconsistencies. It provides the structured feature space required to build predictive models regarding a batter's likelihood to challenge in specific conditions.
  • Defense Subset: This dataset isolates game situations where the pitcher or catcher could challenge (pitch was called a ball and their team has at least one challenge remaining). It maps metrics such as pitch framing, setup positions, catcher challenge rates, and umpire interaction tendencies. This structural split ensures that catcher-specific spatial biases are analyzed separately from offensive player performance profiles.

Feature Engineering: Advanced Situational Splits (GetBatterABSChallengeSplits_Final.sql & GetCatcherABSChallengeSplits_Final.sql)

To extract deeper context from the core pitch records, localized feature engineering scripts were deployed to compute aggregated performance baselines across varying situational and operational splits. These scripts transform raw transactional interactions into specialized feature spaces that focus heavily on contextual pressure points, pitch types, and game states.

Situational Query Scripts & Engineered Datasets

  • Catcher Aggregate Query: GetCatcherABSChallengeSplits_Final.sql

  • Engineered Catcher Situational Splits: MLBData-ABSSituationalSplits-Catchers.csv

Dimensions of Engineered Aggregations

  • Home vs. Away Environmental Splits: The data vectors are segregated into home and away profiles to investigate systemic environmental biases, such as localized fan influence, host venue optical calibration variances, and distinct visiting team behavioral patterns under adversarial conditions.
  • Inning Groupings & Resource Availability Constraints: Observations are aggregated by game phase (early, middle, and late leverage innings) and mapped directly against the volume of strategic challenges remaining in the dugout. This feature captures tactical risk-reward shifts, showing how challenge success and aggression thresholds alter when resource limitations become acute and/or opportunities to use remaining challenges become limited.
  • Pitch Type Structural Groupings: Pitch tracking records are partitioned into specific pitch type classifications (fastballs, breaking balls, off-speed deliveries). This dimensionality lets downstream models isolate spatial zone boundary discrepancies based on ball rotation, velocity vectors, and sudden breaks that typically complicate real-time human arbitration.

Database Architecture: Master Index & Lookup Registries

To optimize query execution plans and prevent high dimensional data storage redundancies, static structural dimensions are isolated within dedicated relational lookup registries. These foundational tables anchor transactional pitch entries by providing immutable metadata regarding athlete identities, franchise details, and comprehensive season schedules.

Exploratory Data Analysis

The following ten visualizations provide an empirical, structural exploration of the ABS challenge tracking data. These figures dissect base distributions, spatial umpire accuracy discrepancies, and situational behavioral variances across both batter and defensive data subsets.

EDA Visualization 1: Batter Challenge and Overturn Rates Distributions

Analysis Summary: This figure illustrates the box plot distributions of challenge behaviors among offensive batters across the tracked dataset rows. The distribution profile highlights a tightly clustered interquartile range for baseline challenge rates, though notable outlier positions emerge representing highly aggressive individual batters and batters with few challenges that were either all overturned or all upheld. These outliers were identified as valid values, and will be kept for future modeling.

EDA Visualization 2: Catcher Challenge and Overturn Rates Distributions

Analysis Summary: This figure presents the descriptive box plot metrics for defensive catcher challenge behaviors. A direct comparison with offensive baselines reveals a structurally different median density profile, suggesting that defensive units execute challenge parameters under differing risk-reward thresholds than their offensive counterparts. Similar to batters, the outliers that were flagged in these box plots were identified and cleared as valid.

EDA Visualization 3: Temporal Challenge and Overturn Rates Trends

Analysis Summary: This time series visualization tracks the longitudinal volume and corresponding overturn percentages across the regular season timeline. The moving trend vectors reveal explicit seasonal fluctuations, indicating structural shifts in system adaptation as players and coaching staffs accumulated behavioral experience over consecutive months.

EDA Visualization 4: Spatial Heatmap Analysis of Strike Zone Margins (Batters and Defense)

Analysis Summary: These paired spatial coordinate heatmaps map the offensive and defensive challenge rates to the pitch's distance from the strike zone boundaries. While the strike zone has a fixed width, its bottom and top are dynamic depending on the batter's height and stance, so two heatmaps were required for each challenge type. As expected, high-density color clusters indicate that batter challenges predominantly isolate missed strikes on lower margins, whereas defensive tracking concentrates heavily on framing discrepancies along horizontal edges.

EDA Visualization 5: Inter-Team Challenge and Overturn Rates Comparisons

Analysis Summary: This multi-variable scatter plot maps team-specific performance matrices to evaluate macro organizational efficiencies within the ABS framework. The distinct structural clustering patterns indicate that certain organizations maintain highly optimized video review pipelines, achieving significantly elevated success rates despite lower overall challenge volumes.

EDA Visualization 6: Individual Home Plate Umpire Accuracy and Variance Boxplots

Analysis Summary: This comprehensive box plot profile charts the distribution of challenge and overturn rates across individual categorical profiles of home plate officials. The wide variance spans across differing quartiles, providing explicit evidence of non-uniform human strike zone application and proving the systemic necessity for analytical correction models. The flagged outliers were cleared as valid data.

EDA Visualization 7: Catcher Offensive vs. Defensive Comparisons

Analysis Summary: This scatter chart evaluates the correlation between a catcher's individual offensive challenge accuracy versus their defensive framing tracking efficiency. The absence of a strong directional linear association implies that offensive visual acuity parameters do not necessarily transfer into defensive pitch-framing awareness profiles.
